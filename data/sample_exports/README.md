# Sample exports — 2026-01

Two settlement files in the platforms' own shapes, generated by `generate.py`
with a fixed seed. Unlike `../real_samples/`, which came from outside, these are
built deliberately to exercise everything Fynn has learned about real exports.

Regenerate with:

```bash
python data/sample_exports/generate.py
```

## How confident we are in each structure

**Lazada — high.** The nine columns are exactly what Lazada Seller Center shows
under Finance → Account Statements → Transaction Overview → Export:

```
Transaction Date | Transaction Type | Transaction Number | Order Number
Order Item ID | Item Name | Comment | Amount | Statement Period
```

Every `Transaction Type` is one of the 99 verified terms in
`data/lazada_taxonomy.py`. There is deliberately **no Fee Classification
column**, because the real export has none — that field comes from the API.

**Shopee — lower.** The wide order-level shape and the fee names are verified,
but Shopee's exact header list is not, in the way Lazada's now is. Treat the
column order and the presence of any individual tax column as provisional.

## What each file holds

| | Shopee | Lazada |
|---|---|---|
| Layout | wide — one row per order | long — one row per transaction |
| Rows | 60 orders + 4 adjustments | 459 transaction lines |
| Melts to | 543 settlement lines | 459 settlement lines |
| Distinct labels | 21 | 31 |
| Payout | **3,733.38** | **3,194.59** |

Loaded together: one `2026-01` cycle, 1,002 lines, **32 exceptions**. Approving
all 32 ties both platforms to 0.00 with balanced journals.

### Cross-checked against the screenshots

| Check | Result |
|---|---|
| Nine columns, in order | exact match with the Transaction Overview export |
| Every `Transaction Type` | all 31 appear in the verified 99-term taxonomy |
| The six fees on the one real order we have sight of | all present |
| `Statement Period` format | `05 Jan 2026 - 11 Jan 2026` — see below |

**What is still not verified:** the `Statement Period` *format*. The column name
comes from the Transaction Overview header, but that table was empty on screen.
`14 Dec 2020 - 20 Dec 2020` is the only period format seen on a real Lazada
screen — in the order-detail view, under the heading `Account Statement` — so
the sample uses that shape. Fynn parses the ISO form (`2026-01-05 - 2026-01-11`)
equally well; only the sample's choice is a judgement call.

## What is planted, and what it tests

**Shopee**

- Adjustments as a **second block inside the same file**, under their own header
  after a blank line — the layout platforms are known to vary on.
- The last adjustment references an order that is not in the statement, so it
  surfaces as an orphan refund rather than an unknown fee.
- 5 cancelled orders carrying a refund and a reverse shipping fee.
- `AMS Commission Fee` on affiliate orders only, `Withholding Tax` and
  `Lost Compensation` on a handful — so column presence is sparse, not uniform.
- Every row's components sum exactly to its `Final Amount`. That identity is
  what proves the melt lost nothing; the file is rejected outright if it fails.

**Lazada**

- **Four weekly statement periods**, the last running `2026-01-26 - 2026-02-01`.
  All four fold into one `2026-01` cycle, because a period is named by where it
  starts. This is the file to reach for when revisiting the assumption that a
  cycle is a calendar month — it isn't, and Fynn currently patches over that.
- Fee names Fynn has never seen but Lazada publishes: `Promotional Charges
  Bundles`, `LCP Fee`, `Seller Picks Commission`, `Lazada Bonus`, `Pick Up Fee`.
- **Refunds written the way Lazada writes them.** There is no line called
  "Refund". A return reverses each original row separately, in a different
  classification: `Reversal Item Price`, `Reversal Commission`,
  `Payment Fee Credit`, `Reversal Promotional Charges Vouchers` and
  `Return shipping fees`. Ten orders are returned, a third of them partially, so
  the reversals are proportional rather than whole. An engine expecting a refund
  to be one line will not tie out — which is the point.
- **Promotions on ~70% of orders**, across six voucher terms, because that is
  the bulk of what a firm actually has to classify.
- **Third-party logistics on ~22% of orders** — `Shipping Fee (Charged By 3P)`
  with `FBL Handling Fee` and `Import Duties and Tax (Charged by 3PL)` behind it,
  plus account-level `Inventory Storage Fees` and `DPP Service Fee`. In the one
  real order the screenshots show, the 3P shipping charge was the single largest
  deduction, so a sample without it was not representative.
- Six lines with **no order number at all** — storage, pick-up, balance
  adjustments, the bonus, and the catch-all fee.
- A reversal whose sale settled in a previous statement, so it has no matching
  order here.
- `The fee that does not belong to the terms above`, which must never acquire a
  rule however often it is approved.
- 14 lines carry a `Comment`. These flow into the investigator's prompt and the
  explainer's context, and on an adjustment the comment usually *is* the answer.

## Expected exception profile

All 23 are genuine judgement calls — every mechanical fee is absorbed by the
starter pack. They divide as:

- vouchers, discounts, coins, campaign, LCP and bundle charges — marketing
  expense, or a reduction of revenue
- service and withholding taxes — recoverable or not, by jurisdiction
- compensation, bonus and balance adjustments — income, or an offset
- two orphan refunds — per-order judgements that must not become rules
- one catch-all fee — deliberately unruleable
